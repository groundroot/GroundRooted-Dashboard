## 0. 문서 상태와 개정 범위

이번 산출물은 설계서다. 사이트 화면, 프로토타입, 코드, DB, 결제 연동, 앱 인증 모듈, 배포는 제작하거나 변경하지 않는다. 아래 모션·시연·성능 수치는 향후 제작 지침 및 검수 목표이며 실제 구현 또는 측정 결과가 아니다.

기존 `groundrooted-site-spec-v1.1.md`의 이메일 인증, 통합 계정, 구매 이력, 제품 사용 권한, 기기 인증의 구분은 유지한다. v1.2에서 정리한 다음 요구사항을 유지하고, v1.3에서 19–23절의 기술·디자인·검수 기준을 추가한다.

| 구분 | 확정된 요구사항 |
|---|---|
| 사이트의 성격 | 전문적인 소프트웨어 브랜드·판매 사이트. 구매해도 믿을 수 있다는 인상을 실제 정보와 경험으로 뒷받침한다. |
| 메인 페이지 | `/`에서 GroundRooted와 모든 앱을 소개한다. |

| 첫 상세 페이지 | PDF를 Markdown으로 변환해 보유 자료를 AI 작업에 활용하도록 준비하는 앱부터 설계한다. |
| 표현 방식 | 제품 브랜딩, 가치 중심 히어로, 실제 작동 시연, 결과 확인, 구매 가치 설명을 포함한다. |

`PDF to MD`는 현재 문서에서 사용하는 작업명이다. 정식 제품명, 지원 OS, 실제 앱 화면, 변환 품질, 처리 위치, 가격과 판매 정책은 아직 이 문서에서 확정하지 않는다. 스타일·카피·모션의 세부 선택은 아래 제안안이다.

## 1. 브랜드와 제품의 관계

### 1.1 브랜드 홈과 제품 페이지의 역할

GroundRooted 홈은 어떤 도구들을 만드는 브랜드인지 설명한다. 개별 제품 페이지는 방문자가 그 제품을 이해하고, 작동을 확인하고, 가격과 조건을 검토해 구매하는 공간이다.

**브랜드 홈은 제품을 발견하는 곳이고, 제품 페이지는 구매 판단에 필요한 근거를 제공하는 곳이다.**

제품 페이지의 히어로는 별도 사이트가 아니라 각 제품 상세 페이지의 첫 구간이다. 히어로 아래에 사용 과정, 결과, 구매 가치, 지원 범위, 가격이 하나의 흐름으로 이어진다.

### 1.2 브랜드 체계

공통으로 유지할 것은 GroundRooted 로고, 기본 서체, 여백 체계, 버튼 규칙, 계정·지원 경험, 푸터다. 제품별로 바뀌는 것은 앱 이름·아이콘, 핵심 문구, 실제 화면, 기능 설명, 사례, 강조 색상과 핵심 모션이다.

제품마다 완전히 다른 회사의 사이트처럼 보이게 만들지 않는다. 반대로 제품명과 아이콘만 교체한 동일한 템플릿으로 끝내지도 않는다.

### 1.3 경로

```text
/                                  GroundRooted 브랜드 홈·전체 앱 소개
/typecut                           Typecut 제품 상세·판매
/transcribe-grabber                트랜스크라이브 그랩퍼 제품 상세·판매
/pdf-to-md                         PDF to MD 제품 상세·판매 — 첫 설계 대상

/pdf-to-md/help                     해당 제품 사용 안내 — 콘텐츠 확보 후 공개
/pdf-to-md/changelog                해당 제품 업데이트 기록 — 실제 기록만 공개

/login                             공통 이메일 로그인
/auth/verify                       이메일 인증
/checkout                          선택한 제품의 구매·결제
/checkout/result                   주문 처리 결과
/account                           내 계정 요약
/account/library                   보유 앱 목록
/account/library/{slug}            구매한 제품별 사용·인증 관리
/account/orders                    전체 구매 이력
/account/orders/{orderId}           주문 상세
/account/licenses                  제품 권한·기기 인증
/account/settings                  이메일·계정·세션 관리
/support                           공통 고객지원
/terms                             이용약관
/privacy                           개인정보 처리방침
/refund-policy                     구매 취소·환불 안내
/admin                             운영자 전용 관리
```

`/products/<slug>`는 신규 공개 제품 주소로 사용하지 않는다. 이전 설계 경로가 이미 공개된 경우에만 새 경로로 영구 리디렉션하고 내부 링크·공유 주소를 함께 수정한다. 실제 배포 여부는 확인되지 않았으므로 리디렉션을 설정했다고 표현하지 않는다.

`login`, `account`, `auth`, `checkout`, `support`, `admin`, `api`, 정책 페이지명 등 시스템 경로는 제품 slug로 사용할 수 없게 예약한다. 제품 ID는 URL과 별개로 유지해 제품명 변경이 과거 주문과 라이선스를 바꾸지 않게 한다.

## 3. 시각 디자인 방향

### 3.1 기본 인상

‘화려한 AI 실험 사이트’가 아니라 **정돈되어 있고, 실제로 작동하며, 오랫동안 사용할 수 있는 전문 도구의 판매 사이트**를 지향한다.

기본안은 밝은 뉴트럴 배경, 짙은 본문, 절제된 녹색 강조다. 화면 전체에 그라데이션·발광·입자를 반복하지 않는다. 전환을 집중해서 보여줄 한 구간에만 어두운 배경을 적용하는 구성을 검토한다.

기존 프로토타입의 색상·레이아웃은 확정된 브랜드 자산으로 간주하지 않는다. 실제 앱 화면과 함께 비교해 최종 선택한다.

| 요소 | 제안 기준 |
|---|---|
| 배경 | 소프트 화이트와 밝은 회색. PDF 원문과 앱 화면을 읽기 쉽게 한다. |
| 텍스트 | 그래파이트 계열. 핵심 문장은 높은 대비, 보조문도 충분한 가독성을 확보한다. |
| 강조 | 깊은 에메랄드 계열을 구매·진행 상태·핵심 변화에 제한적으로 사용한다. |
| 히어로 제목 | 데스크톱 64–88px, 모바일 36–44px를 시작점으로 검토한다. 한국어 줄바꿈을 기기별로 조정한다. |
| 본문 | 데스크톱 18–20px, 모바일 16–18px를 시작점으로 검토한다. |
| 레이아웃 | 데스크톱 콘텐츠 최대 폭 약 1200px. 긴 설명은 별도로 폭을 좁힌다. |
| 여백 | 데스크톱 주요 구간 112–160px, 모바일 64–88px를 시작점으로 검토한다. |
| 제품 화면 | 과도하게 기울이지 않는다. 핵심 텍스트를 실제로 읽을 수 있는 크기로 보여준다. |
| 카드 | 기능 개수 채우기용 카드 그리드를 피하고 구매 가치가 다른 경우에만 나눈다. |
| 이미지 | 실제 앱, 실제 PDF, 실제 MD를 중심으로 한다. AI 로봇·우주·추상 네트워크 이미지를 제품 증거로 사용하지 않는다. |
| 서체 | 한글·영문이 일관되게 보이는 조합을 선택한다. 상업용 웹 사용 권한과 배포 조건을 확인한다. |

### 3.2 공통 내비게이션

글로벌 헤더는 GroundRooted, 앱 탐색, 고객지원, 로그인·내 계정을 제공한다. 앱 탐색 항목은 세 제품의 루트 경로로 연결한다.

개별 제품에는 제품명, 개요, 작동 방식, 결과 보기, 가격, 구매·관리 버튼으로 구성된 제품 내비게이션을 둔다. 긴 상세 페이지에서는 제품 내비게이션만 고정해 화면을 과도하게 차지하지 않게 한다.

모바일은 주요 메뉴를 축약하고 구매 영역이 본문·쿠키 안내·접근성 컨트롤을 가리지 않게 한다. 버튼은 영상 재생 완료나 긴 애니메이션 시청을 요구하지 않고 바로 사용할 수 있어야 한다.

## 4. GroundRooted 메인 페이지 설계

메인부터 모든 세부 기능을 설명하지 않는다. 첫 상세 페이지인 PDF to MD에서 정한 품질을 메인과 다른 제품으로 확장한다.

**브랜드 문구 초안**

> 반복을 줄이고, 중요한 일에 깊이를.
>
> 영상 편집부터 자료 정리까지. GroundRooted의 도구로 다음 작업을 준비하세요.

| 순서 | 역할 | 구성 |

| 1 | 브랜드 이해 | 브랜드 문구, 핵심 앱 화면, 앱 살펴보기 |
| 2 | 대표 제품 | 첫 설계 제품인 PDF to MD의 가치와 실제 화면, 제품 보기 |
| 3 | 전체 앱 탐색 | Typecut, 트랜스크라이브 그랩퍼, PDF to MD를 각각 아이콘·한 문장·실제 화면·출시 상태와 함께 소개 |
| 4 | 구매 후 경험 | 하나의 이메일 계정으로 보유 제품·다운로드·구매 이력·인증을 관리한다는 안내 |

세 앱의 시연을 동시에 자동 재생하지 않는다. 출시 전 제품은 상태를 표시하고 구매 가능한 것처럼 보이게 하지 않는다. 홈에서 모든 앱의 존재를 알 수 있어야 하므로 전체 앱을 보기 위해 별도의 `/products` 방문을 요구하지 않는다.

앱 카드는 목적·대표 결과·출시 상태를 보여주고 각 제품의 작동 방식으로 연결한다. 상세 소개에서는 9.4절의 과정·결과 컴포넌트로 실제 사용을 이해하게 한다. 배경은 사용자 지정 Molten Metal을 hero에 적용하며 내용의 가독성과 정적 대안을 함께 제공한다.

## 5. PDF to MD의 제품 정의와 구매 가치

### 5.1 제품 정의

**보유한 PDF를 Markdown으로 변환해, AI 작업과 지식 정리에 다시 사용할 자료로 준비하는 앱.**

현재 확인된 사용자 요구는 PDF 입력과 Markdown 결과 제공이다. 변환 품질, 지원 PDF 범위, 파일 처리 위치, 앱에 내장된 AI 전송 기능은 실제 제품 확인 전 확정하지 않는다.

### 5.2 판매 메시지의 중심

‘파일 확장자를 바꾼다’보다 ‘이미 가지고 있는 자료를 다음 작업에 다시 쓴다’를 앞세운다. 다만 사용자가 얻을 수 있는 가치와 아직 검증하지 않은 자동화 기능을 혼동하지 않는다.

| 구매 가치 | 상세 페이지에서 설명할 내용 | 필요한 증거 |
|---|---|---|
| 자료 준비의 반복을 줄인다 | PDF에서 활용할 텍스트를 매번 다시 준비하는 대신, 변환된 MD를 작업의 출발점으로 삼는다. | 실제 변환·저장 과정. 절약 시간은 측정 전 숫자로 쓰지 않는다. |
| AI에게 전달할 내용을 직접 확인한다 | 변환 결과를 읽고, 필요한 내용을 고르고, 사용자가 선택한 AI 작업에 전달한다. | 원본·MD 비교와 사용자 전달 단계. 자동 전송처럼 연출하지 않는다. |
| 한 번 준비한 자료를 다시 활용한다 | 변환된 파일을 노트·연구·강의·업무 자료로 보관하고 재사용하는 흐름을 보여준다. | 실제 내보낸 파일과 별도 도구에서 여는 예시. |

Obsidian은 노트를 Markdown 기반 일반 텍스트 파일로 저장한다고 공식 안내한다.[T1] 이를 파일 활용 예시의 근거로 삼되, GroundRooted 앱에 Obsidian 자동 동기화 기능이 있다는 뜻으로 사용하지 않는다.

### 5.3 ‘PDF 직접 입력’과의 차별화

Claude 공식 문서는 PDF를 직접 처리하고 텍스트·이미지·차트 등을 분석하는 기능을 설명한다.[T2] 따라서 ‘AI는 PDF를 읽지 못하므로 이 앱이 꼭 필요하다’는 주장을 사용하지 않는다.

이 제품의 차별화는 **자료를 한 번 분석하고 끝내는 것과 달리, 사용자가 확인·수정·재사용할 수 있는 Markdown 결과를 갖는 작업 흐름**에 둔다. 특정 자료에서 직접 PDF를 활용하는 편이 더 적합할 수 있다는 점을 부정하지 않는다. Markdown 변환이 모든 시각 정보를 보존하거나 모든 AI의 응답을 개선한다고 약속하지 않는다.

‘AI 학습 완료’, ‘AI가 영구적으로 기억’, ‘환각 방지’, ‘모든 AI와 자동 연결’, ‘토큰 비용 절감’ 같은 표현은 실제 기능과 검증 없이 사용하지 않는다. 기본 표현은 ‘AI에 참고 자료로 전달’ 또는 ‘AI 작업용 자료로 준비’다.

## 6. PDF to MD 히어로

### 6.1 제안 카피

**제품 표기**  
PDF to MD · by GroundRooted

**메인 제목**

> 쌓아 둔 PDF를,  
> AI와 일하는 자료로.

**설명**

> 가지고 있는 PDF를 Markdown으로 변환해,  
> AI에게 전달하고 다시 활용할 수 있는 자료로 준비하세요.

**버튼**  
작동 방식 보기 / 구매하기

제품이 실제 판매 가능한 상태가 되기 전에는 ‘구매하기’를 공개 결제로 연결하지 않는다. 개발 단계라면 개발 중 표시와 확보된 실제 시연만 제공한다. 체험판이 확인되지 않았으므로 ‘무료로 시작’ 버튼을 기본값으로 넣지 않는다.

가격·OS·처리 조건이 확정되면 버튼 아래에 간결하게 표시한다. 미정 값을 임의의 가격·무제한·평생 이용·로컬 처리 문구로 대체하지 않는다.

### 6.2 화면 구성

상단에는 짧은 메시지와 두 버튼, 하단에는 실제 앱 화면을 크게 배치한다. 화면 안에서 ‘PDF 선택 → 실제 변환 → MD 결과 확인·저장’이 드러나게 한다. 기기 외형보다 앱 인터페이스와 결과물에 초점을 맞춘다.

히어로는 제품의 작동을 요약한 약 12–18초 무음 영상 또는 이에 준하는 인터랙티브 재생을 제안한다. 반드시 재생·정지 수단과 정지 화면 대체물을 둔다. 소리나 긴 로딩을 강요하지 않는다.

PDF·MD 문서가 이동하는 설명용 그래픽을 보조로 사용할 수 있지만, 실제 앱의 기능 증거는 실제 녹화와 결과물로 분리한다. 그래픽에서 제목이나 표가 정교하게 변형되었다고 실제 앱이 해당 구조를 정확히 복원한다고 주장하지 않는다.

## 7. PDF to MD 상세 페이지 전체 흐름

**전체 서사: 관심 → 문제 인식 → 작동 이해 → 결과 확인 → 활용 가치 → 불안 해소 → 구매 판단.**

| 구간 | 방문자의 질문 | 제목·메시지 초안 | 핵심 화면·근거 | 다음 행동 |
|---|---|---|---|---|
| S01 히어로 | 나에게 어떤 가치가 있나? | 쌓아 둔 PDF를, AI와 일하는 자료로. | 실제 앱 화면과 변환 요약 | 작동 방식 보기 |
| S02 문제 | 왜 이 도구가 필요한가? | 모아 둔 자료, 다시 활용하고 있나요? | 자료를 다시 준비하는 작업과 MD 결과를 사용하는 작업의 차이 | 과정 살펴보기 |
| S03 전환 스토리 | 어떻게 바뀌나? | 파일을 바꾸는 일에서, 자료를 활용하는 일로. | PDF → 변환 → MD 확인 → 활용의 4단계 | 결과 확인 |
| S04 결과 비교 | 내 파일에도 믿고 쓸 만한가? | 결과를 먼저 확인하세요. | 실제 PDF·실제 MD·읽기 미리보기 | 샘플 파일 확인 |
| S05 실제 사용 영상 | 내가 사용할 수 있나? | 선택하고, 변환하고, 다음 작업으로. | 클릭부터 저장까지 실제 제품 사용 과정 | 사용 안내 |
| S06 구매 가치 | 구매 뒤 무엇이 달라지나? | 한 번 준비한 자료를, 다음 작업에도. | 자료 준비·전달 전 검토·재사용의 세 장면 | 활용 예시 탐색 |
| S07 신뢰와 지원 범위 | 내 자료는 안전한가? 무엇을 지원하나? | 맡기기 전에, 확인할 수 있도록. | 처리 위치·전송·보관·지원 파일·제한·지원 환경 | 상세 정책 |
| S08 가격과 이용 조건 | 무엇을 얼마에 사는가? | PDF to MD를 내 작업에 더하세요. | 실제 가격·과금·기간·기기·업데이트·환불·지원 | 구매 또는 제품 관리 |
| S09 FAQ | 아직 남은 궁금증은? | 구매 전 확인하세요. | 직접 PDF 입력과의 차이, OCR, 표·수식, AI 전송, 제한 | 해당 답변·지원 |
| S10 마지막 행동 | 지금 무엇을 하면 되나? | 다음 작업은, 이미 가진 자료에서. | 제품 한 줄 요약, 구매·시연, 기존 구매 확인 | 구매 또는 내 제품 |

### 7.1 문제를 과장하지 않는 S02

문구는 ‘당신의 PDF는 쓸모없다’가 아니라 ‘가진 자료를 다시 활용하는 데 드는 준비가 있다’에 맞춘다. PDF를 직접 사용할 수 있는 환경을 숨기지 않는다. 사용자 인터뷰나 측정이 없다면 모두가 특정 시간을 낭비한다고 숫자를 붙이지 않는다.

### 7.2 구매 가치를 설명하는 S06

기능 명사만 나열하지 않고 실제 작업을 보여준다.

**자료 준비:** 보고서의 내용을 MD로 준비해 다음 분석의 출발점으로 삼는 장면.  
**전달 전 검토:** 어떤 내용이 추출되었는지 읽고 필요한 부분을 선택하는 장면.  
**다음 작업에 재사용:** 같은 자료를 노트에 보관하고, 이후 강의·리서치·업무에서 다시 사용하는 장면.

앱 내부에 없는 편집·노트·채팅 화면을 앱 기능처럼 합성하지 않는다. 별도 도구의 화면에는 ‘내보낸 파일 활용 예시’를 표시한다. 외부 도구의 로고 사용과 화면 재현 범위를 확인한다.

## 8. 핵심 스크롤 애니메이션 스토리보드

### 8.1 목적

PDF가 MD로 바뀌는 과정과 그 결과를 어디에 쓰는지, 방문자가 스크롤하며 단계적으로 이해하도록 한다. 모든 섹션에 효과를 넣는 대신 **대표 모션 한 구간**을 충분히 정교하게 만든다.

데스크톱에서는 S03을 전체 약 240–280svh의 구간으로 검토한다. 한 화면을 고정하고 내부 장면을 전환하되 브라우저의 스크롤 입력을 가로채지 않는다. 스크롤을 많이 해야 구매할 수 있는 구조로 만들지 않는다. 이 길이는 초기 연출안이며 사용성 검수 후 축소할 수 있다.

| 구간 내 진행 | 화면 | 문구 | 연출 규칙 |
|---|---|---|---|
| 0–25% | 선택한 실제 샘플 PDF와 앱 진입 화면 | 시작은, 가지고 있는 PDF. | 문서 여러 장은 자료의 존재를 설명하는 배경일 뿐 일괄 변환 기능을 뜻하지 않게 한다. |
| 25–50% | 앱에서 확인된 변환 단계 | 다음 작업에 쓸 형태로. | 실제 지원 동작을 근거로 확대·하이라이트한다. 처리 엔진 내부를 추정해 시각화하지 않는다. |
| 50–75% | 같은 PDF의 실제 MD 결과가 주 화면이 됨 | 결과를 보고, 필요한 내용을 고르세요. | 제목·문단·목록·표는 실제 결과에 있는 것만 보여준다. |
| 75–100% | MD 저장 후 별도 작업에 활용하는 장면 | 이제, 내 자료로 다음 작업을. | 앱이 담당하는 변환·저장과 사용자가 수행하는 외부 도구 전달을 명확히 분리한다. |

각 단계는 스크롤뿐 아니라 번호 버튼으로도 확인할 수 있게 한다. 정지 상태에도 문서·단계·설명을 이해할 수 있어야 한다.

### 8.2 다른 모션의 역할

| 종류 | 적용 | 제안 범위 |
|---|---|---|
| 히어로 진입 | 메시지와 앱 화면의 차분한 등장 | 약 450–650ms. 핵심 내용을 오래 숨기지 않는다. |
| 기능 포커스 | 설명하는 위치의 확대·색상 강조 | 실제 UI를 읽기 위한 움직임만 사용한다. |
| 작은 상호작용 | 버튼, 탭, 아코디언, 구매 상태 전환 | 약 180–240ms. 흔들림·과도한 탄성을 기본값으로 쓰지 않는다. |
| 제품 내비게이션 | 긴 페이지에서 현재 구간·구매 상태 유지 | 레이아웃 점프 없이 표시한다. |
| 마무리 | 결과 화면에서 다음 구간으로 복귀 | 갑작스러운 카메라 이동이나 화면 전체 회전을 피한다. |

타이핑 효과로 AI가 실시간 응답하는 것처럼 꾸미거나, 가짜 진행률로 실제 변환 속도를 암시하지 않는다. 초 단위 수치는 애니메이션 연출 길이이며 앱 처리 시간 광고가 아니다.

### 8.3 모바일·모션 감소

모바일에서는 긴 고정 스크롤 대신 네 단계가 일반 문서 흐름으로 이어지게 한다. 실제 앱 영상과 결과 확인은 유지하되 데스크톱의 축소판을 강요하지 않는다.

운영체제의 동작 줄이기 설정에서는 위치 이동·확대·패럴랙스를 제거하고 동일한 정보를 정적 장면과 단계 버튼으로 제공한다. W3C는 상호작용으로 발생하는 비필수 모션을 끌 수 있게 하는 접근을 설명한다.[Q1]

자동으로 시작하고 다른 콘텐츠와 함께 5초를 넘게 움직이는 콘텐츠에는 일시정지·중지·숨김 수단을 제공하는 것이 WCAG의 해당 기준이다.[Q2] 이 설계에서는 히어로 영상에도 명시적인 재생·정지를 제공한다.

## 9. 사이트 안에서 작동을 보여주는 방식

판매 페이지의 시연을 세 종류로 구분한다. ‘버튼을 눌러 볼 수 있다’는 이유만으로 실제 변환 서버가 연결된 것처럼 표시하지 않는다.

### 9.1 설명용 모션

PDF → MD → 활용이라는 개념을 소개한다. 실제 앱 화면이 아닌 그래픽에는 ‘변환 과정 설명’ 등의 표시를 둔다. 미구현 기능을 이미 판매하는 것처럼 연출하지 않는다.

### 9.2 실제 앱 영상

현재 앱에서 공개 가능한 샘플을 선택하고, 변환하고, 결과를 확인하고, 파일을 저장하는 장면을 녹화한다. 자세한 영상은 약 45–60초를 시작점으로 편집한다. 기다리는 부분을 자르거나 배속할 경우 화면에 표시한다.

OS·앱 버전·샘플 유형을 기록한다. 변환 결과를 영상 밖에서 손으로 고친 뒤 자동 변환 결과처럼 제시하지 않는다. 외부 편집을 보여줄 경우 별도 작업임을 표시한다.

### 9.3 인터랙티브 결과 샘플

초기안은 **미리 변환해 검증한 공개 샘플을 웹에서 탐색하는 결과 데모**다. 방문자 파일 업로드와 실시간 변환 기능은 별도 범위로 두고 기본 요구사항에 자동 추가하지 않는다.

데스크톱은 원본 PDF와 MD를 나란히 보여준다. 오른쪽은 Markdown 원문과 읽기 미리보기 사이를 전환할 수 있게 한다. 모바일은 원본·MD·미리보기 탭으로 나눈다.

PDF와 MD는 레이아웃이 다르므로 이미지를 겹치는 단순 전후 슬라이더를 주 비교 수단으로 쓰지 않는다. 필요하면 특정 문단을 대응시키되, 사이트에서 만든 비교용 대응 표시를 앱의 자동 출처 추적 기능처럼 광고하지 않는다.

샘플 원본과 결과 파일은 로그인 없이 확인할 수 있게 설계한다. ‘실제 앱 변환 결과’, 샘플의 유형, 앱 버전, 변환 조건, 확인된 제한을 함께 표시한다. 파일이 아직 없을 때 가짜 다운로드 버튼을 공개하지 않는다.

### 9.4 앱 소개를 이해시키는 컴포넌트

각 앱은 입력→앱에서 하는 작업→실제 결과→지원 한계를 직접 탐색할 수 있게 소개한다. React Bits Stepper 기반 WorkflowDemo에서 단계를 선택하면 관련 화면·짧은 설명·결과가 함께 바뀐다. 실제 제품을 웹에서 다시 구현하는 것이 아니라 검증한 공개 샘플과 녹화를 탐색하는 컴포넌트다.

- PDF to MD: S03 스크롤 이야기는 유지하고 S05에 수동 과정 탐색을 둔다. S04의 원본 PDF·MD 원문·읽기 보기를 연결해 입력과 결과를 대조한다.
- Typecut: 실제 자막 편집 단계와 같은 구간의 편집 전/후를 비교한다. 기능 탭을 선택하면 해당 실제 화면·무엇이 달라지는지·제한을 보여준다. 지원 형식과 편집 기능은 실제 앱 확인 후 공개한다.
- 트랜스크라이브 그랩퍼: 스크립트 확보·확인·저장을 단계별로 보여주고 실제 저장된 텍스트를 확인·복사하게 한다. 실시간 URL 수집이나 영상/음성 다운로드·AI 요약을 새 기능으로 추가하지 않는다.

자동 넘김 없이도 처음/이전/다음/다시 보기와 단계 직접 선택이 가능하고 마지막 결과를 유지한다. 모바일·키보드·모션 감소·JS 실패에서도 과정 요약과 실제 결과를 읽을 수 있어야 한다. 미확보 자산을 가짜 화면·다운로드·성공 상태로 대체하지 않는다. [React Bits 계획 2.1절](groundrooted-react-bits-plan-v1.0.md)의 AC01–AC03, 실행 계획 T26이 구현·검수 기준이다.

## 10. 신뢰를 만드는 정보 설계

### 10.1 신뢰는 디자인과 근거가 함께 만든다

| 고객이 느끼는 불안 | 제공할 근거 | 위치 |
|---|---|---|
| 실제로 존재하고 작동하는 앱인가? | 현재 앱 화면, 변환 과정, 실제 결과 파일 | 히어로·작동 영상·결과 비교 |
| 내 PDF에도 적합한가? | 지원 PDF 유형, 언어, 복잡한 문서 처리 범위, 샘플과 제한 | 결과 비교·지원 환경·FAQ |
| 자료가 외부로 나가는가? | 처리 위치, 외부 전송 대상, 보관·삭제, 사용자가 제어할 수 있는 범위 | 신뢰 구간·정책 |
| 무엇을 구매하는가? | 과금 방식, 사용 기간, 기기 수, 업데이트 범위, 추가 비용 유무 | 가격 카드·결제 확인 |
| 문제가 생기면 지원받는가? | 실제 문의 경로, 설치 안내, 업데이트 기록, 지원 정책 | 제품 내비게이션·가격·푸터 |
| 이미 산 제품을 잃어버리지 않는가? | 공통 이메일 계정, 구매 이력, 재다운로드·제품 관리 | 구매 안내·내 계정 |

공개 제품 페이지는 로그인 없이 충분히 읽을 수 있게 한다. 시연과 지원 조건을 확인하기 위해 먼저 가입하도록 막지 않는다.

### 10.2 확인 전 사용하지 않는 표시

‘100% 로컬’, ‘절대 외부 전송 없음’, ‘무제한’, ‘평생 업데이트’, ‘오류 없는 OCR’, ‘표·수식 완벽 보존’, ‘모든 AI 자동 연동’, ‘공식 인증’, ‘검증된 보안’은 근거 없이 사용하지 않는다.

후기, 별점, 사용 기업 로고, 누적 사용자 수, 처리량, 성공률, 환불 보장 기간도 실제 증거·동의·정책이 있을 때만 표시한다. 다른 프로젝트의 처리 성과를 이 앱의 성과로 옮겨 적지 않는다. 후기 확보 전에는 실제 결과물과 제작·지원 정보로 신뢰를 설명한다.

### 10.3 데이터 처리와 AI 전달은 분리해 설명한다

PDF 변환 자체가 로컬이어도 사용자가 결과를 외부 AI에 보내는 단계는 별개의 데이터 전송이다. 앱의 처리 범위와 사용자가 선택한 외부 서비스의 범위를 한 문장의 ‘내 자료는 안전합니다’로 합치지 않는다.

파일 처리 위치·전송·보관·삭제 정책이 확인되지 않은 상태에서는 공개 판매를 위한 개인정보 관련 카피를 확정하지 않는다. 앱 안에 외부 AI 전송 기능이 있다면 대상 서비스·전송 내용·동의·비용을 별도로 명시한다.

## 11. 가격·구매·제품 관리

### 11.1 가격 영역

가격, 결제 방식, 지원 OS, 사용 기간, 기기 수, 업데이트 권리, 환불·지원 안내가 한 묶음으로 보이게 한다. 가격을 알기 위해 이메일을 제출하게 하지 않는다.

제품 정책이 정해지지 않았는데 Basic·Pro·Team 등 가상의 3단계 요금제를 만들지 않는다. 할인 기준이 없는 취소선 가격, 가짜 카운트다운, 좌석 부족 문구를 사용하지 않는다.

설치형·웹형 여부와 요금 정책이 확정되면 버튼을 ‘구매하기’, ‘다운로드’, ‘앱 열기’ 등 실제 행동에 맞게 정한다. 외부 AI 서비스 이용료가 필요하다면 제품 가격에 포함되는지 구분한다.

### 11.2 상태별 버튼

| 상태 | 제품 판매 페이지의 동작 |
|---|---|
| 미로그인 | 공개 가격·설명·시연을 제공하고 구매 시 이메일 인증으로 이동 |
| 로그인·미구매 | 구매 가능 여부와 이용 조건 확인 후 결제 |
| 구매 상태 확인 중 | 공간을 유지한 확인 상태. 미구매로 단정하지 않음 |
| 조회 실패 | 다시 확인·고객지원. 재구매로 유도하지 않음 |
| 결제 확인 중·권한 발급 지연 | 주문 처리 안내. 같은 제품의 중복 결제를 막음 |
| 권한 유효 | 다운로드 또는 실행, 제품 관리, 해당 구매 내역 |
| 권한 유효·기기 미등록 | 구매 완료 표시와 별도 설치·인증 안내 |
| 환불·권한 회수 | 이력 유지, 현재 사용 불가 사유, 지원 경로 |
| 기간형 만료 | 정책에 따른 만료 정보·갱신. 기간형 정책이 있을 때만 적용 |
| 신규 판매 중지 | 신규 구매만 제한. 기존 구매자의 주문·사용 권한은 별도 판정 |

개인별 구매 영역은 공개 제품 콘텐츠와 분리해 다른 고객에게 캐시되지 않게 설계한다. 이메일·주문 전체 내역을 공개 제품 화면에 과도하게 노출하지 않는다.

| A10 | 구매·라이선스 정책 | 가격·결제·내 계정 | 금액·통화·과금·기간·기기·업데이트·환불·지원 확정 |
| A11 | 지원 문서·업데이트 기록 | 제품 지원 | 실제 작동하는 문의 경로와 실제 변경 내용 |
| A12 | 제품별 공유 이미지 | 외부 링크 미리보기 | 실제 제품 자산 활용, 다른 앱과 구분 |

마케팅용 샘플은 고객 자료나 개인 정보가 포함된 실제 업무 파일을 무단 공개하지 않는다. 앱 버전·입력 파일 유형·설정·원본·결과·촬영일을 한 묶음으로 기록한다. 변환 품질을 높이기 위한 수동 수정을 했다면 이를 명시한다.

## 14. 모바일·접근성·성능 검수 목표

### 14.1 기본 사용성

영상이 재생되지 않아도 제품의 역할·가치·가격·지원 조건을 알 수 있어야 한다. 자바스크립트나 모션 초기화가 실패했다고 제목과 설명이 투명 상태로 남지 않게 한다. 필수 메시지를 영상 안에만 넣지 않는다.

키보드로 제품 내비게이션, 영상, 샘플 탭, FAQ, 구매 버튼에 접근할 수 있어야 한다. 비교 영역의 텍스트는 읽고 복사할 수 있게 구성하고 이미지에만 의존하지 않는다. 스크롤 모션을 끈 상태에서도 순서와 의미를 유지한다.[Q1][Q2]

### 14.2 목표 수치

Google의 Core Web Vitals 권고는 LCP 2.5초 이내, INP 200ms 이하, CLS 0.1 이하이며 모바일·데스크톱을 구분한 실제 방문의 75번째 백분위로 판단한다.[Q3] 이를 운영 단계의 품질 목표로 채택한다. 실제 측정 결과는 아직 없다.

초기 성능 예산안은 ‘첫 화면의 핵심 정적 자산을 먼저 표시하고 영상·추가 데모는 이후 로드’하는 방식이다. 영상 로딩 때문에 제목·구매 영역을 숨기지 않는다. 하단 시연은 필요 시 로드하고 화면 밖 동영상은 정지한다. 이미지·영상 영역 크기를 미리 확보해 구매 버튼 위치가 갑자기 바뀌지 않게 한다.

배포 전에는 대표 모바일·데스크톱 환경에서 실험실 측정을 하고, 배포 후에는 실제 사용 데이터를 확인한다. 실험실 점수만으로 실제 사용자 INP와 전체 성능을 검증했다고 보고하지 않는다.[Q3]

## 15. 기존 서비스 설계에서 유지할 시스템 원칙

이번 디자인 개정이 기존의 계정·구매·인증 요구를 대체하지 않는다.

**계정:** 이메일 인증으로 신규 가입과 기존 로그인을 연결한다. 주문과 권한은 이메일 문자열이 아니라 고유 사용자 ID에 연결한다. 인증 후 원래 제품 또는 주문으로 돌아가며, 이메일 확인만으로 결제를 실행하지 않는다.

**상태:** 이메일 소유 확인, 주문·결제 상태, 제품 사용 권한, 기기 등록을 별도 상태로 둔다. 웹형 제품처럼 기기 등록이 필요 없는 경우는 ‘해당 없음’으로 처리한다.

**결제:** 서버가 제품·가격·통화·소유권·기존 구매를 확인한다. 성공 화면이나 클라이언트 데이터만으로 권한을 발급하지 않는다. 중복 통지와 재시도는 중복 권한을 만들지 않게 처리하고, 결제 후 권한 반영 장애는 복구한다.

**환불:** 주문 이력은 남긴 채 정책에 따라 해당 구매의 권한을 회수한다. 다른 정상 구매의 권한까지 잘못 회수하지 않는다. 기기 등록 해제는 환불이나 구매 이력 삭제가 아니다.

**앱 인증:** 실제 앱이 동일한 서버의 제품 사용 권한을 확인하게 한다. 웹에 인증 배지를 붙이는 것으로 구현 완료로 보지 않는다. 지원 환경에 맞는 연결 방식과 오프라인 정책은 별도 확정한다.

**데이터:** 사용자, 제품, 페이지 콘텐츠, 가격·정책, 주문·항목, 결제 이벤트, 권한, 기기 등록, 배포 버전, 감사 기록을 구분한다. 과거 구매 조건은 현재 가격이나 페이지 수정으로 바뀌지 않도록 보존한다.

**권한·지원:** 고객은 본인의 주문과 권한만 조회·관리한다. 공개 제품 콘텐츠에 개인별 주문 정보가 섞이지 않게 한다. 관리자 작업은 별도 권한과 기록을 요구한다. 문의·환불·기기 변경 지원과 실패 재처리 절차를 둔다.

**콘텐츠 운영:** 실제 화면·지원 조건·다운로드 버전을 함께 관리한다. 제품명·slug·가격·판매 상태를 페이지마다 중복 작성해 불일치가 생기는 구조를 피한다. 페이지 자산에는 관련 앱 버전과 검증 상태를 기록한다.

v1.3에서 웹 프레임워크·모션·인증·저장 기술을 19절의 설계 기준으로 선정했다. 실제 설치·계약·구현·배포를 완료한 것은 아니다. 국내 원화 판매를 가정한 결제 기술 기본안과, 아직 미정인 판매 국가·계약 가능 여부를 구분한다.

## 16. 측정과 출시 순서

### 16.1 향후 측정할 행동

시연 재생, 결과 샘플 확인, 가격 구간 방문, 결제 시작, 결제 완료, 지원 문의를 제품별로 집계하는 구성을 검토한다. 방문자의 문서 내용, 원문 파일명, 이메일, 인증번호를 마케팅 이벤트에 넣지 않는다. 개인정보 관련 수집·동의 조건은 실제 운영 범위에서 검토한다.

애니메이션의 평가는 효과가 많다는 인상이 아니라 제품 이해, 결과 확인, 구매·지원 동선에 도움이 되는지로 판단한다. 근거 없는 목표 전환율이나 수익 증가율을 이 문서에서 약속하지 않는다.

### 16.2 제작 순서

```text
PDF to MD 실제 기능·화면·결과물 확인
→ 제품 가치와 페이지 카피 확정
→ PDF to MD 정적 상세 페이지 디자인
→ 대표 스크롤 모션·실제 시연 설계 확정
→ 모바일·모션 감소·구매 상태까지 설계
→ GroundRooted 홈에 제품 소개 경험 확장
→ Typecut·트랜스크라이브 그랩퍼에 공통 품질 기준 적용
→ 별도 구현 단계에서 계정·결제·실제 앱 인증·배포·검수
```

전체 앱과 백엔드를 동시에 크게 만들기보다 첫 제품의 설명·증거·브랜딩 품질을 먼저 확정한다. 나머지 앱은 같은 디자인 규칙을 공유하되 각자의 가치와 작동을 설명한다.

### 16.3 남은 결정

정식 제품명, 현재 앱 화면, 지원 OS·PDF 종류·언어·크기, OCR·표·수식·이미지·일괄 처리 지원, 처리 위치·외부 전송, 가격·과금·기간·기기 수·업데이트·환불, 실제 도메인·판매 국가·결제 계약 가능 여부는 확인 후 확정한다. 기술 구현의 결제 기본안은 19절을 따른다. 미정 항목을 홍보 문구로 먼저 약속하지 않는다.

다음 상세 디자인 판단에 가장 먼저 필요한 자료는 **현재 PDF to MD 앱 화면 또는 실제 변환 과정을 담은 짧은 영상과, 공개 가능한 입력·출력 샘플 한 쌍**이다.

## 17. 프로젝트 Wiki 인계 메모

이번 작업은 사용자의 Mac, iCloud vault, GitHub 저장소, 운영 DB를 변경하지 않는다. 실제 구현을 시작하는 환경에서 공용 vault의 `WIKI.md`와 해당 프로젝트 파일을 먼저 읽고, 재사용할 결정을 `## 메모` 아래에 추가한다. 자동 생성 영역은 덮어쓰지 않는다.

인계할 결정:

> GroundRooted의 루트 `/`는 전체 앱을 소개하는 브랜드 홈이다. 제품 상세는 `/products/<slug>`가 아니라 `/<slug>`이다. 첫 설계 대상은 `/pdf-to-md`. 중심 가치는 보유 PDF를 MD로 준비해 AI 작업과 지식 정리에 재사용하는 것이다. 대표 스크롤 모션, 실제 앱 영상, 실제 원본·MD 비교, 가격·지원·처리 조건으로 신뢰를 설명한다. 자동 AI 전송·OCR·로컬 처리·성능 등은 검증 전 약속하지 않는다. 공통 이메일 계정과 제품별 구매·사용 권한·기기 인증 체계는 유지한다. 현재 단계는 설계서이며 사이트 구현은 별도다.

## 19. 기술 스택과 시스템 아키텍처

### 19.1 선택 원칙과 적용 범위

이번 선택은 **제품 설명의 완성도, 실제 작동 시연, 신뢰할 수 있는 구매·인증, 작은 운영팀의 유지보수**를 함께 만족시키기 위한 것이다. 애니메이션을 위해 계정 시스템을 따로 만들거나, 제품마다 다른 인증·결제 플랫폼을 붙이지 않는다.

프런트엔드와 웹 서버를 하나의 Next.js 프로젝트에 두고 회원·데이터·배포 파일은 관리형 Supabase에 둔다. 기존 PDF 변환 앱의 언어·변환 엔진은 확인되지 않았으므로 이 문서에서 새 언어로 재작성하도록 지시하지 않는다. 웹사이트는 판매·계정·인증 연결을 담당하고 PDF 변환 계산은 기존 앱의 책임으로 남긴다.

### 19.2 채택 스택

| 영역 | 선택 | 구체 사용 범위 | 도입 시점 |

### 19.3 버전·현재 문서에 대한 적용 규칙

Next.js 16과 React 19 조합을 기준으로 하되, 정확한 패치 버전은 구현 착수일의 보안 공지와 패키지 호환성을 확인해 고정한다. `latest`·canary·실험 기능을 상용 배포의 무조건적 기본값으로 두지 않는다. pnpm 잠금파일을 커밋하고 CI는 고정 설치를 사용한다. UI 소스를 복사해 쓰는 shadcn/ui는 생성 도구 버전·primitive 종류·가져온 소스 revision도 기록한다.[N01][N03]

2026년 7월 shadcn/ui 공식 변경 안내는 신규 프로젝트의 기본 기반을 Base UI로 바꾸고 Radix 지원은 유지한다고 설명한다. 이번 신규 프로젝트는 **Base UI 계열만 선택**한다. 이전 Radix 예제의 props·구조를 섞어 넣지 않는다. 기존 다른 프로젝트를 이 결정 때문에 마이그레이션하지 않는다.[N03]

운영 런타임은 Node.js 24를 지정한다. 로컬·CI의 버전과 Vercel의 major를 일치시키되 Vercel 관리형 런타임의 minor·patch는 플랫폼이 갱신할 수 있으므로 정확한 운영 patch까지 영구 고정했다고 주장하지 않는다.[N17]

Supabase 변경 이력에서 확인한 항목을 반영한다. Node.js 20을 신규 기준으로 쓰지 않고, 새 테이블의 Data API 자동 노출에 의존하지 않으며, 이메일 템플릿·발신 도메인은 자체 SMTP로 구성한다. `@supabase/ssr`는 공식 SSR 문서의 실제 API에 맞춰 고정하고 변경 시 회귀 테스트한다. 새 서버 SDK가 있다는 이유만으로 문서와 혼용하지 않는다.[N05][N22][N23][N24]

### 19.4 공개 화면과 개인 데이터의 경계

```text
방문자·구매자
      │
      ▼
Vercel / Next.js
  ├─ 공개 콘텐츠: 홈, /pdf-to-md, /typecut, /transcribe-grabber
  │     ├─ 서버에서 HTML 우선 제공
  │     └─ GSAP·영상·샘플 뷰어만 필요한 시점에 로드
  ├─ 개인 영역: /account, 주문, 다운로드·인증 관리
  └─ 서버 API: 결제 확인, 권한 판정, 기기 등록, 운영자 작업
        ├─ Supabase Auth / Postgres / Storage
        ├─ Toss Payments: 결제 사업자
        └─ Resend: 이메일 전달

각 실제 앱 ── 사용자 인증 + HTTPS ── License API ── 같은 제품 권한
```

공개 소개는 Server Component와 정적 생성·캐시를 우선하고, 애니메이션·영상 컨트롤·구매 상태처럼 상호작용이 필요한 부분만 Client Component로 분리한다. 페이지 전체에 일괄적으로 `use client`를 붙이지 않는다. 검색 제목·설명·OG·canonical·사이트맵은 제품별로 구성한다.[N01]

인증 상태와 개인 구매 정보는 공용 캐시에서 제외한다. 공개 가격·판매 가능 여부도 서버 상품 데이터와 연결하되 실제 결제 직전에 다시 확인한다. 결제 중 가격이 바뀌면 새 금액을 설명하고 고객이 확인하게 한다. 마케팅 MDX나 브라우저가 전달한 금액으로 결제를 확정하지 않는다.

초기 공개 페이지를 Auth 서버의 응답에 종속시키지 않는다. Auth가 지연되어도 제품 설명·가격 안내·샘플은 볼 수 있고, 개인 구매 패널만 확인 지연 상태가 된다. 인증 쿠키 갱신 응답과 공개 캐시 응답이 섞이지 않도록 경로·fetch 정책·헤더를 검수한다.

### 19.5 제품 콘텐츠와 상거래 데이터의 기준점

| 데이터 | 기준점 | 수정 경로 |
|---|---|---|
| 제품의 고유 ID·slug·판매 상태 | Postgres 제품 레코드 | 운영자 화면·검증된 초기 데이터 |
| 현재 가격·통화·이용 조건 | Postgres 가격·정책 레코드 | 운영자 화면, 버전·변경 기록 |
| 소개문·섹션 배치·FAQ·사용법 | 저장소의 MDX·React | 변경 리뷰 → 미리보기 → 배포 |
| 앱 화면·시연·샘플 | Storage와 자산 manifest | 실제 제품 검증 후 버전별 게시 |
| 구매 시 가격·이용 조건 | 주문 항목 snapshot | 서버 주문 생성 시 고정 |
| 보유 여부·사용 권한 | entitlement 레코드 | 확인된 결제 또는 감사되는 운영자 조정 |
| 색상·서체·여백·모션 | 승인된 디자인 토큰 | 토큰 기준본 변경 → Figma·코드 반영 |

제품 manifest는 제품 ID를 참조한다. 제품명을 파일마다 복제하지 않고, 같은 ID의 공개 콘텐츠와 상거래 정보를 조합한다. 슬러그 변경은 ID를 바꾸지 않으며, 이미 공개된 주소는 리디렉션한다. 알려지지 않은 slug는 404다.

MDX는 운영자가 검토한 저장소 콘텐츠에만 사용한다. 사용자나 앱이 만든 MD를 MDX로 실행하지 않는다. 변환 결과에는 react-markdown을 사용하고 raw HTML 실행은 금지한다. 외부 이미지와 링크는 허용 정책으로 제한하고 임의 스크립트·iframe을 실행하지 않는다.[N10]

초기에는 Sanity·Contentful 같은 별도 CMS를 추가하지 않는다. 비개발 운영자의 일상적인 편집 수요가 생기면 콘텐츠 편집만 확장한다. 주문·정책의 기준 데이터를 CMS로 복제하지 않는다.

### 19.6 데이터 모델과 권한

| 핵심 데이터 | 역할·주요 제약 |
|---|---|
| auth users / profiles | 고유 계정 ID, 인증 이메일, 계정 상태. 이메일 문자열로 소유권 연결 금지 |
| consent_records | 동의 문서 버전·시점·경로. 필수/선택 동의 구분 |
| products / prices / policy_versions | 고유 ID, 예약 경로 제외 slug, 현재 판매 상태·가격·정책 |
| orders / order_items | 고객 ID, 상태, 정수 금액·통화, 상품·정책 snapshot |
| payments / payment_events | 사업자+거래 ID, 이벤트 중복 방지 키, 처리 상태 |
| entitlements | 고객·제품·원천 주문 항목, 유효 기간·상태. 원천의 중복 발급 금지 |
| activations | entitlement·설치 식별자, 상태·등록·해제·최근 확인 시점 |
| releases | 제품·버전·OS·배포 경로·체크섬·게시 상태 |
| outbox_jobs | 처리할 업무·재시도·다음 실행 시각·잠금·오류 요약 |
| audit_logs / support_tickets | 운영자 변경 사유·추적 ID, 고객지원 상태. 비밀 원문 제외 |

노출 스키마의 테이블에는 RLS와 최소 GRANT를 함께 적용한다. 고객 읽기는 인증 역할만으로 허용하지 않고 본인 user_id 조건을 함께 검사한다. public view를 만든다면 기반 테이블의 접근 제어를 우회하지 않는 방식인지 확인한다.[N06][N23]

고객에게는 자신의 구매 조회 권한만 필요한 만큼 허용한다. 가격 변경, paid 상태 쓰기, 권한 발급, 환불 확정, 관리자 권한 부여는 서버 전용이다. 업데이트 정책에는 기존 행의 접근 조건과 변경 후 행의 조건을 모두 명시한다. 사용자 수정 가능 metadata를 관리자 권한의 근거로 쓰지 않는다.[N06]

Supabase를 브라우저에서 사용할 때 publishable key만 사용한다. secret/service_role key는 서버 전용이며 고객 세션용 클라이언트와 분리한다. SQL의 원자적 반영이 필요한 작업은 실행 권한을 제한한 DB 함수로 묶는다. 단순히 오류를 없애기 위해 SECURITY DEFINER를 붙이지 않는다. 서비스 전용 함수는 PUBLIC·anon·authenticated 실행을 막고 필요한 서버 역할만 허용하는 것을 기본안으로 삼는다.

### 19.7 이메일·세션 설계

Supabase Auth의 이메일 OTP를 채택하고, 인증 메일은 Resend를 custom SMTP로 연결한다. 주문·지원 메일은 Resend 서버 API로 보낸다. 앱 화면에서 ‘이메일 확인 완료’와 ‘제품 사용 가능’을 별도 상태로 표시한다.[N04][N08]

OTP 요청·검증·재전송·실패 상태를 설계한다. 6자리 입력은 복사·붙여넣기와 자동 완성 가능한 하나의 논리 입력으로 다룬다. 인증 유효 시간·재전송 간격은 설정과 UI를 일치시킨다. 문서의 예시 코드나 고정 OTP는 상용 코드에 넣지 않는다.

Supabase의 기본 자동 가입 동작을 그대로 방치하지 않는다. 신규 계정 생성을 허용하는 경로는 필요한 가입 동의를 먼저 받도록 구성한다. 기존 사용자 로그인 경로에서는 자동 생성 옵션을 제어한다. 계정 존재 여부를 과도하게 드러내지 않는 응답과 재시도 정책을 설계한다.[N04]

서버는 getClaims 또는 적합한 검증으로 토큰을 검증하고, 민감한 작업에는 최신 사용자 상태·권한·필요한 세션 유효성도 확인한다. JWT 서명이 유효하다는 사실만으로 환불·관리자 권한·정지 상태를 결정하지 않는다. getSession에서 읽은 사용자 객체만으로 서버 인가를 통과시키지 않는다.[N05]

쿠키·토큰 처리는 공식 SSR SDK 모델에 따른다. 모든 토큰이 HttpOnly라고 문구만 적고 브라우저 SDK를 병용하지 않는다. Secure·SameSite·Origin/CSRF 방어·허용 복귀 경로를 실제 방식에 맞춰 검수한다. 이메일 변경 후에도 고유 계정 ID의 구매는 유지한다.

발신 도메인 인증과 스팸·반송 처리, 로그인 메일과 마케팅 동의 분리, 메일 실패 재시도·지원 경로를 준비한다. 운영자 계정은 일반 고객보다 강한 재인증·다중 인증과 실시간 서버 권한 검사를 적용한다.

### 19.8 결제·환불·복구 설계

**기술 기본안은 국내 원화 판매에 대한 Toss Payments SDK v2다.** 국내 판매를 확정했다는 의미는 아니다. 해외 우선 판매로 결정되면 판매자 자격·국가·통화·세금 책임을 확인한 뒤 결제 어댑터를 교체한다. Stripe·Paddle·Lemon Squeezy를 가입 가능 여부 확인 없이 동시에 도입하지 않는다.

주문서의 브랜드 영역은 자체 디자인하고, 결제수단 선택·약관 등은 결제 사업자의 공식 위젯을 사용한다. 결제 iframe 내부를 임의 CSS로 바꿀 수 있다고 전제하지 않는다.

```text
구매 선택 → 서버에서 제품·현재 가격·기존 구매 확인
→ 대기 주문 생성 → 결제 사업자 화면
→ 서버 승인/거래 조회 → 금액·통화·주문·최종 상태 검증
→ DB에서 주문 완료 + entitlement + outbox 원자 반영
→ 고객의 주문 화면·제품 관리 갱신
```

토스 v2 흐름에 맞춰 paymentKey·orderId·amount를 서버의 주문 정보와 비교하고 승인 결과를 확인한다. 성공 URL 도착은 결제 완료의 충분한 근거가 아니다.[N09]

웹훅은 사업자가 문서화한 방식으로 검증하고 필요하면 비밀 키로 거래를 재조회한다. 모든 PG에 동일한 서명 헤더가 있다고 가정하지 않는다. 승인·중복 웹훅·재조회가 같은 권한을 여러 번 발급하지 않게 한다. 환불 뒤 늦은 결제 이벤트가 권한을 되살리지 못하도록 최종 거래 상태와 상태 전이 규칙을 검사한다.

외부 PG 승인과 우리 DB 반영은 하나의 트랜잭션이 아니다. 승인 후 DB 실패를 위해 대기 주문 재조회, 멱등 반영, 작업 경보를 둔다. 메일 발송 실패는 이미 승인된 주문·권한을 되돌리지 않는다. Vercel Cron이 outbox를 주기적으로 처리하며, 동시 실행 잠금·재시도 상한·오류 큐·수동 재처리 경로를 둔다. Cron은 웹훅의 대체물이 아니라 누락·장애 복구 경로다.[N18]

구독·분할·부분 환불·번들은 관련 정책과 상태 전이를 정의한 뒤 추가한다. 상거래 데이터 모델은 확장을 막지 않되 미정 상품 유형을 판매 UI에 미리 만들지 않는다.

### 19.9 실제 앱 인증과 다운로드

라이선스의 기준 데이터는 entitlements다. 웹사이트와 실제 앱이 같은 서버를 조회한다. 첫 연결 기본안은 앱에서도 공통 Supabase 이메일 계정으로 인증하고, 앱의 access token을 공통 License API에 전달하는 것이다. 웹 로그인 쿠키가 설치형 앱에 자동 공유된다고 가정하지 않는다.

앱의 실제 프레임워크를 유지하고 공식 SDK 또는 HTTPS 인터페이스로 연결한다. 네이티브 앱의 토큰은 지원 OS의 안전한 자격증명 저장소에 보관하고, 브라우저 확장은 해당 실행 환경에 맞춰 별도 검수한다. 앱 안에 서버 secret/service_role key를 넣지 않는다. 동일 이메일 계정이더라도 사용 권한은 제품별로 조회한다.

```text
앱에서 공통 계정 인증
→ License API에서 사용자·제품·기기 조건 확인
→ 원자적으로 기기 등록 또는 기존 등록 재확인
→ 현재 사용 권한 반환
→ 웹 계정 화면에도 같은 상태 표시
```

기기 식별자는 최소 수집한 설치 식별자와 공개 기기 이름을 기본으로 한다. 하나의 요청에서 서로 다른 기기가 동시에 남은 한 자리를 차지하지 못하도록 DB 잠금·고유 제약으로 처리한다. 기기 해제는 구매 이력을 삭제하지 않는다.

오프라인 사용 여부·유예 기간은 제품 정책에 따라 별도로 확정한다. 오프라인을 제공한다면 서버 서명과 만료·기기 범위를 갖춘 권한 증명, 키 교체, 환불 반영 지연을 추가 설계해야 한다. 서명 URL이나 웹 로그인 성공을 오프라인 라이선스로 재사용하지 않는다. 이 문서는 영구 무제한 오프라인 사용을 기본 제공한다고 약속하지 않는다.

공개 시연 자산과 실제 설치 파일은 Storage 버킷을 분리한다. 설치 파일은 비공개 버킷에 저장하고 서버가 제품·버전·권한을 확인한 뒤 짧은 유효기간의 다운로드 URL을 제공한다. 서명 URL은 기간 안에 전달될 수 있는 링크이며, 다운로드 후 파일 복제를 막는 DRM 자체가 아니다.[N07]

설치형 제품은 지원 OS에 맞는 배포 서명·검증, 체크섬, 버전 안내를 출시 요건으로 확인한다. 확인되지 않은 공증·보안 인증 배지를 만들지 않는다.

### 19.10 시연·모션 기술 상세

**히어로:** 정적 포스터를 첫 화면에서 먼저 표시하고, 영상은 이후에 준비한다. `video`에는 무음·인라인 재생·정지 컨트롤을 두며 자동 재생 실패 시 포스터와 재생 버튼을 유지한다. 보이지 않는 영상은 멈춘다. 모바일·데이터 절약 상황에서는 사용자 시작을 우선한다.

**대표 스크롤:** GSAP timeline + ScrollTrigger의 scrub·pin 기능으로 S03을 구현한다. `@gsap/react`로 React 생명주기와 정리를 관리한다. 데스크톱에서만 pin을 켜고 모바일·reduced-motion에서는 정적 단계형으로 전환한다. 변환 시연에 무관한 Lenis·강제 smooth scroll을 추가하지 않는다.[N11]

**성능·오류:** 스크롤 매 프레임에 React state를 갱신하지 않고 DOM의 transform·opacity 위주로 움직인다. 부모 pin 요소 자체는 움직이지 않고 자식 stage를 움직인다. 폰트·이미지 크기가 확정된 시점에 위치를 재계산한다. 라우트 이동·resize 시 생성한 타임라인·이벤트를 정리한다. 단계를 안내하는 React 상태는 단계가 실제 바뀔 때만 갱신한다.

**결과 비교:** PDF.js는 PDF를 보여주는 용도이고 변환 엔진이 아니다. 확인된 실제 PDF와 MD 한 쌍을 manifest로 연결한다. 원문 MD는 선택·복사 가능하게, 읽기 미리보기는 react-markdown과 remark-gfm으로 표시한다. 기본 샘플은 미리 변환한 결과임을 표시한다. PDF worker는 선택한 라이브러리 버전과 일치시키고 필요할 때만 로드한다.[N10][N12]

원본·결과가 없을 때 가짜 완성 화면·다운로드를 공개하지 않는다. 마케팅용 샘플은 공개 허가된 자료만 사용한다. 파일 전체를 초기 HTML·JS에 포함하지 않고 요청 시 로드한다. 임의 외부 URL을 서버가 대신 다운로드하는 API는 기본 데모에 만들지 않는다.

### 19.11 검토용 폴더 구조

아래는 향후 구조 명세이며 생성된 소스 트리가 아니다.

```text

  (marketing)/[slug]/page.tsx             /pdf-to-md 등
  (marketing)/[slug]/help/page.tsx
  (marketing)/[slug]/changelog/page.tsx
  (auth)/login/page.tsx
  (account)/account/...
  checkout/...

  api/downloads/...

src/components/
  ui/                                    Base UI 기반 기초
  brand/                                 헤더·푸터·로고 영역
```

폴더 이름의 route group은 실제 URL에 나타나지 않게 한다. `/products/<slug>`를 새 공개 주소로 만들지 않는다. 동적 제품 route가 account·api·support 같은 시스템 경로를 침범하지 않도록 registry와 예약 slug 검사를 둔다.

### 19.12 운영·환경·비용의 경계

개발·검토·운영 DB와 결제 키를 분리하고, 검토 배포에는 실제 고객 데이터를 복제하지 않는다. 미리보기 배포와 Storybook은 필요 범위만 접근 가능하게 하며 실제 토큰·주문 데이터 대신 fixture를 사용한다.

GitHub Actions에서 타입·로직·브라우저·접근성·빌드를 검사하고 검토 배포를 만든다. 배포 설정은 이 통과 결과를 필수 조건으로 삼는다. 단순 Git push만으로 검사 전 운영 배포가 먼저 일어나지 않게 한다. DB 변경은 이전 웹 버전과 공존할 수 있는 확장→이행→정리 방식으로 설계하고 복원·롤백 절차를 기록한다.

Vercel 공식 조건에 따라 앱 판매 사이트의 배포는 Pro를 기본으로 잡는다. Hobby는 비상업적 개인 사용으로 제한된다. 무료 플랜으로 영구 상업 운영이 가능하다고 가정하지 않는다.[N16]

Supabase의 운영 요금제·백업/PITR·로그 보존, Resend 발송량, 영상·파일 트래픽, 결제 수수료는 별도 예산으로 확인한다. 한 가지 정액 요금이 모든 비용을 포함한다고 표시하지 않는다. DB 백업뿐 아니라 Storage 파일의 별도 보존·복구도 검토한다. 실제 리전·국외 전송·개인정보 처리 조건은 계정 생성 전에 확인하고 법적 적합성을 이 문서가 보증하지 않는다.

Sentry에는 이메일·OTP·원문 파일명·문서 본문·인증 토큰을 보내지 않도록 마스킹한다. 초기 Session Replay는 꺼 둔다. web-vitals 및 자체 최소 이벤트로 시연 확인·가격 도달·결제 시작을 관찰하고 실제 구매 완료 수는 검증된 주문 데이터를 기준으로 집계한다. 분석 수집 범위와 동의 요건은 운영 정책에 맞춘다.[N19][N20]

### 19.13 처음에는 도입하지 않는 기술

선택한 스택은 애플이 사용하는 내부 기술을 알아냈다는 뜻이 아니다. Apple에서 참고한 **장면 중심 제품 설명**을 GroundRooted의 유지 가능한 기술로 구현하는 설계다.

## 20. GroundRooted Design System 1.0

### 20.1 시스템의 목적과 언어

**핵심 인상: 차분한 전문성, 분명한 제품 가치, 읽을 수 있는 실제 화면, 예측 가능한 구매 경험.**

디자인 시스템은 색상표만이 아니라 색·서체·간격·컴포넌트·반응형·모션·상태·문구·검수 규칙을 묶은 계약이다. 사용자는 제품을 바꿔도 로그인·구매·관리 방법을 다시 배울 필요가 없어야 한다.

브랜드와 고객 계정은 같은 규칙을 사용한다. 제품별로 변경할 수 있는 것은 아이콘·강조색·시연 자료·제품 카피·대표 장면이다. 제품별 가격과 라이선스 상태의 의미, 버튼 높이, 글자 체계, 접근성 규칙은 바꾸지 않는다.

### 20.2 토큰 구조와 기준본

```text
Primitive                     Semantic                     Component
색상·크기 원값           →     역할을 뜻하는 이름       →     실제 부품의 값
forest.800                    action.primary.bg             button.primary.background
stone.50                      surface.canvas                page.background
space.6                       component.padding             card.padding
```

일반 컴포넌트는 hex 값이나 임의 간격을 직접 쓰지 않고 semantic token을 참조한다. 제품별 강조색은 product.accent로, 성공·위험 같은 상태는 status token으로 분리한다. 초록색 제품이라는 이유로 모든 상태가 성공처럼 보이게 하지 않는다.

이 설계서의 제안 토큰을 초기 기준본으로 삼는다. 구현 착수 시 버전 관리되는 토큰 파일을 기준으로 하고 Tailwind `@theme`·CSS 변수·Figma 변수의 이름을 대응시킨다. Figma가 변경됐다는 이유만으로 운영 코드가 자동 갱신된다고 전제하지 않는다. 토큰 변경과 디자인·코드·Storybook 반영을 한 변경 묶음으로 기록한다.[N02][N13]

### 20.6 서체와 타이포그래피

기본 서체는 **Pretendard Variable 하나로 한글·영문 UI를 통일**한다. Markdown 원문·주문 식별자 등은 `ui-monospace` 계열 시스템 고정폭 폰트를 사용한다. 필요하지 않은 추가 디스플레이 폰트를 얹지 않는다. Pretendard의 공식 OFL 조건을 확인하고 실제 배포 시 필요한 라이선스 고지를 유지한다. 이번 산출물에는 폰트 파일을 포함하지 않는다.[N15]

| 스타일 | 모바일 | 태블릿 | 데스크톱 | 굵기·행간·용도 |
|---|---:|---:|---:|---|
| display.hero | 40px | 64px | 80px | 650, 1.12, 히어로 H1 |
| heading.section | 32px | 40px | 48px | 650, 1.20, 섹션 제목 |
| heading.feature | 24px | 28px | 32px | 600, 1.30, 기능·가치 제목 |
| heading.card | 20px | 22px | 24px | 600, 1.35, 카드·제품명 |
| body.lead | 18px | 20px | 20px | 400–450, 1.65, 히어로 보조 설명 |
| body.default | 16px | 18px | 18px | 400, 1.70, 상세 설명 |
| ui.label | 15px | 15px | 16px | 550–600, 1.40, 버튼·라벨 |
| caption | 14px | 14px | 14px | 400–500, 1.55, 버전·촬영·파일 조건 |
| code.preview | 14px | 15px | 15px | 400, 1.65, MD 원문 |

제목 자간은 -0.025em을 시작값으로 하되 한국어 가독성이 나빠지면 줄인다. 본문은 기본 0이다. 제목에는 의미 단위의 한국어 줄바꿈과 `word-break: keep-all`을 적용하고 긴 URL·주문번호에는 안전한 줄바꿈을 허용한다. 고정 높이로 한글·영문 문구를 잘라내지 않는다.

픽셀값은 설계 기준이고 실제 구현에서는 rem과 반응형 clamp로 연결한다. 320px·확대 환경에서는 H1의 의미가 유지되는 범위에서 36px까지 낮추거나 줄 수를 늘린다. 입력 글자는 모바일 확대 동작을 고려해 최소 16px로 둔다. 가격·파일 크기·기기 수는 tabular 숫자를 사용한다.

Pretendard는 자체 호스팅을 기준으로 필요한 문자 범위의 서브셋·WOFF2를 사용하고 전체 한글 파일들을 일괄 preload하지 않는다. 외부 폰트 CDN 지연으로 핵심 카피가 사라지지 않게 fallback을 둔다. 정확한 용량은 실제 사용 범위로 측정한다.

1024px 이상이면서 높이·입력 환경이 적합한 경우에만 대표 스크롤 pin을 켠다. 짧은 화면, 세로 공간 부족, 모션 감소 상태에는 정적 단계 흐름을 사용한다. 모바일에서 억지 가로 스크롤·hover 전용 정보·자동 재생 캐러셀을 사용하지 않는다.

계정 주문표는 작은 화면에서 의미 있는 요약 카드로 전환하되 주문번호·상태·금액·상세 진입은 유지한다. 파일 비교·MD 원문처럼 실제 긴 콘텐츠가 있는 영역만 내부 스크롤을 허용한다.

아이콘은 필요한 것만 가져온다. 의미 있는 아이콘에 접근 가능한 이름을 주고, 텍스트를 중복하는 장식 아이콘은 보조기기에서 중복 읽지 않게 한다.[N21]

모든 카드에 강한 그림자를 넣지 않는다. 앱 화면·모달 등 실제로 표면 분리가 필요한 곳에만 강조한다. backdrop blur는 제품 내비게이션 같은 제한된 구간에서만 사용하고 지원되지 않아도 충분한 배경색을 둔다.

앱 아이콘은 각 제품의 승인된 독립 자산으로 제작하고 시스템 아이콘을 그대로 앱 로고로 쓰지 않는다. GroundRooted 로고의 실제 형태는 미확정이며 이 문서가 새 로고를 제작한 것은 아니다.

### 20.9 버튼·입력·상태 컴포넌트

| 부품 | 규격·variant | 반드시 설계할 상태 |
|---|---|---|
| Button | primary / secondary / ghost / destructive / inverse; 높이 44·48·52px, 좌우 20–24px | default, hover, focus-visible, pressed, loading, disabled |
| TextField | 높이 48px, 16px 글자, 12px radius, 고정 label·도움말 | empty, filled, focus, error, disabled |

| Badge | 텍스트+선택 아이콘, status 토큰; 비동작 요소 | neutral, info, success, warning, error |
| Tabs | 44px 이상 조작 높이, 선택 표시+문구 | active, focus, disabled, panel loading/error |
| Accordion | 48px 이상 질문 행, 제목·펼침 표시 | open, closed, focus; 높이 변화는 절제 |

primary 버튼은 화면의 주요 결정 영역에서 하나를 중심으로 한다. 히어로의 구매와 작동 방식 보기는 primary/secondary로 우선순위를 다르게 둔다. 키보드 포커스는 2px outline과 3px offset을 기본으로 하며 제거하지 않는다. 조작 영역은 최소 44×44px를 내부 기준으로 삼는다.

loading 중에도 버튼 너비를 유지하고 설명을 ‘확인 중…’처럼 행동에 맞게 바꾼다. 거래 진행은 낙관적으로 ‘구매 완료’로 표시하지 않는다. 같은 버튼의 반복 입력을 막아도 서버 멱등성 검사는 별개로 필수다.

영수증·환불·기기 해제처럼 중요한 결과는 자동으로 사라지는 toast만으로 끝내지 않고 본문 상태도 갱신한다. 결제 실패와 권한 확인 불가의 문구를 구분한다. form label을 placeholder로 대체하지 않는다.

### 20.12 모션 시스템

| 토큰·유형 | 기준 | 적용 |
|---|---|---|
| motion.instant | 0ms | 권한·보안·필수 상태 반영 |
| motion.fast | 160ms | 버튼·색·아이콘의 작은 변화 |
| motion.ui | 220ms | 탭·아코디언·패널 변화 |
| motion.section | 480ms | 보조 섹션의 한 번만 등장 |
| motion.hero | 600ms | 앱 프레임 등 장식 진입; H1은 처음부터 읽힘 |
| ease.out | `cubic-bezier(.22,1,.36,1)` | 차분한 등장·안착 |
| ease.standard | `cubic-bezier(.2,0,0,1)` | UI 상태 전환 |
| offset.enter | 최대 16px | 작은 등장 이동 |
| scale.enter | 0.98 → 1 | 미디어 강조, 텍스트 전체 확대 금지 |
| motion.scroll | 스크롤 진행에 종속 | 시간 길이가 아닌 0–100% 장면 상태 |

스크롤 이야기의 기본 전체 높이는 데스크톱 약 260svh, 고정 stage는 제품 내비게이션을 제외한 가시 높이다. 실제 스크롤 진행 길이는 이 차이로 계산하고 고정된 픽셀 마법값을 넣지 않는다. 시연이 읽히지 않거나 구매까지 불필요하게 길어지면 길이를 조정한다.

PDF→변환→MD→활용의 네 장면을 0–25–50–75–100%로 나눈다. 한 시점에 하나의 메시지와 하나의 주 화면을 중심으로 한다. 단계 버튼은 해당 장면으로 이동하며, 전체 단계 설명은 보조기기가 순서대로 읽을 수 있게 둔다. 스크롤 갱신마다 aria-live 안내를 반복하지 않는다.

CSS와 GSAP이 같은 요소의 transform을 동시에 제어하지 않도록 소유 영역을 분리한다. 앱 영상의 재생 시간을 스크롤에 억지로 프레임 단위 동기화하는 방식은 기본안에서 제외한다. 영상은 독립 재생, 스크롤 이야기는 HTML/SVG/실제 캡처의 장면 조합으로 만든다.

`prefers-reduced-motion`에서는 pin·이동·scale·parallax를 제거하고 단계 카드를 일반 문서 흐름으로 보여준다. 시연의 정보는 동일해야 한다. 자동으로 움직이는 히어로에는 재생·정지 수단을 제공한다. 접근성 목표는 WCAG 2.2 AA를 중심으로 하며 비필수 상호작용 모션 감소는 추가 설계 기준으로 적용한다.[N25][N26]

### 20.13 영상·결과물·카피 규격

히어로 요약은 12–18초, 자세한 시연은 45–60초를 편집 출발점으로 사용한다. 길이는 제품 속도 광고가 아니다. 고해상도 마스터에서 데스크톱·모바일 목적별 인코딩을 만들고, 실제 앱 화면의 텍스트가 읽히도록 필요한 곳을 잘라 보여준다. 전체 앱 UI를 아주 작게 넣고 4K라는 이유로 읽힌다고 판단하지 않는다.

영상·앱 화면에는 실제 녹화 / 설명용 모션 / 내보낸 파일 활용 예시를 구분해 표시한다. 촬영 앱 버전·입출력 샘플·설정·배속 여부를 기록한다. 성능·후기·기능 증거를 합성하지 않는다.

PDF 샘플은 입력과 실제 MD를 한 쌍으로 제공한다. MD 원문은 장식용 코드 이미지가 아니라 선택·복사 가능한 텍스트다. 영상에 내레이션이 있다면 자막·텍스트 설명을 제공하고, 중요한 내용은 영상 바깥의 HTML에도 존재하게 한다.

문구는 ‘혁신적인 AI 생산성’ 같은 추상어보다 ‘어떤 자료를 어떻게 준비해서 어떤 작업에 쓰는가’를 말한다. 한 섹션에는 하나의 주장과 하나의 증거를 배치한다. 실제 측정 전에는 절약 시간·변환 성공률·토큰 절감률을 적지 않는다.

**PDF→MD 히어로 기준 초안**

> PDF to MD · by GroundRooted  
> **쌓아 둔 PDF를, AI와 일하는 자료로.**  
> 가지고 있는 PDF를 Markdown으로 변환해, AI에게 전달하고 다시 활용할 수 있는 자료로 준비하세요.  
> 구매하기 / 작동 방식 보기

이 카피는 직접 PDF 입력이 불가능하다고 주장하지 않는다. 앱이 자동 AI 전송을 하지 않는다면 저장 후 사용자 전달 단계로 설명한다. 구매 버튼과 가격·OS 표시는 실제 출시·정책 확인 후 공개한다.

### 20.14 Figma와 Storybook의 관리 방식

Figma는 Foundations / Components / Product-PDF-to-MD / Account-Commerce / Motion-Spec / Handoff-Checks의 여섯 영역으로 구성하는 안을 사용한다. 색·간격·radius를 변수로, 서체를 텍스트 스타일로, 버튼·입력·탭을 variant와 Auto Layout으로 정의한다. Light·Inverse와 제품 accent를 별도 계층으로 관리한다. 변수 mode 수와 팀 라이브러리 사용 범위는 실제 Figma 요금제에서 확인한다.[N13]

Storybook은 구현 단계의 실제 컴포넌트 카탈로그다. 부품의 default만 전시하지 않고 loading·error·long Korean text·mobile·reduced motion·구매자/미구매자 상태를 stories로 만든다. 거래·인증 데이터는 fixture로만 사용한다. 운영 DB 키를 넣지 않는다.[N27]

토큰 이름은 Figma와 코드에서 대응 가능하게 유지한다. ‘회색3’, ‘버튼초록최종’ 같은 이름 대신 text.secondary, action.primary.bg처럼 역할이 드러나는 이름을 쓴다. 변경 시 버전·변경 이유·영향 부품·검수 결과를 기록하고 임의의 페이지별 예외를 누적시키지 않는다.

이번 작업은 위 구성의 **명세를 작성한 것**이며 Figma 프로젝트나 Storybook 실행 파일을 생성한 것은 아니다.

### 22.2 품질 예산

Core Web Vitals의 운영 목표는 모바일·데스크톱 각각 실제 방문의 75번째 백분위 기준 LCP ≤2.5초, INP ≤200ms, CLS ≤0.1이다.[N20]

### 22.4 개발 에이전트 인계 규칙

실제 개발 환경에서 사용자 공용 vault의 `WIKI.md`와 해당 `projects/<프로젝트명>.md`를 먼저 읽는다. 그 규칙에 따라 이미 있는 저장소와 상태를 확인한 후 작업한다. 이 설계서는 현재 Mac의 파일 경로나 실제 저장소 브랜치를 확인한 문서가 아니다.

재사용할 결정은 기존 프로젝트 문서의 `## 메모` 아래에만 기록하고 자동 생성 영역을 덮어쓰지 않는다. 이번에 작성한 파일은 대화 산출물이며 vault·GitHub·운영 서비스에 저장하지 않았다.

인계 요약:

> GroundRooted는 하나의 브랜드 홈과 `/<slug>` 제품 페이지를 가진 통합 소프트웨어 스토어다. 첫 제품은 `/pdf-to-md`. Next.js/React/TypeScript, Tailwind 4, shadcn/Base UI, GSAP를 채택한다. Auth·DB·Storage는 Supabase, 이메일은 Resend, 배포는 Vercel Pro다. 국내 원화 판매 가정 시 Toss v2를 사용하되 계약·판매 국가·상품 정책은 별도 확정한다. 기존 앱의 변환 엔진은 재작성하지 않는다. 디자인은 GRDS 1.0 토큰과 구매 상태 계약을 따른다. 실제 시연·실제 결과·제한과 정책이 구매 신뢰의 근거다. 화면·코드·서비스 구현은 아직 수행하지 않았다.
